## The Class File Format

Back to the class file structure from chapter 4 of the official [Oracle JVM Specs](https://docs.oracle.com/javase/specs/jvms/se8/html/jvms-4.html) that we discussed earlier in part one, it looks like this:

```
ClassFile {
    u4             magic;
    u2             minor_version;
    u2             major_version;
    u2             constant_pool_count;
    cp_info        constant_pool[constant_pool_count-1];
    u2             access_flags;
    u2             this_class;
    u2             super_class;
    u2             interfaces_count;
    u2             interfaces[interfaces_count];
    u2             fields_count;
    field_info     fields[fields_count];
    u2             methods_count;
    method_info    methods[methods_count];
    u2             attributes_count;
    attribute_info attributes[attributes_count];
}
```

`u2` means "2 unsigned bytes", and the word next to it is the attribute name, this means that every line describes the size and the name of a class file attribute.


In my ZVM implementation ([src/parser/class_file.rs](https://github.com/muhammadzkralla/zvm/blob/develop/src/parser/class_file.rs)), this translates into a struct:

```rust
pub struct ClassFile {
    pub magic: u32,
    pub minor: u16,
    pub major: u16,
    pub constant_pool_count: u16,
    pub constant_pool: Vec<CpInfo>,
    pub access_flags: u16,
    pub this_class: u16,
    pub super_class: u16,
    pub interfaces_count: u16,
    pub interfaces: Vec<u16>,
    pub fields_count: u16,
    pub fields: Vec<FieldInfo>,
    pub methods_count: u16,
    pub methods: Vec<MethodInfo>,
    pub attributes_count: u16,
    pub attributes: Vec<AttributeInfo>,
}
```

Every field here corresponds exactly to a part of the class file structure in the spec. Now, let me break down each part and explain what it means.

## The Class File Header

The first 8 bytes of a class file are usually referred to as the "header" of the class file. They are used to identify the class file and assure the JVM that this file is a real Java class file and tells the JVM what version of the specs does this class file follow.

### Magic Number

The very first four bytes of any compiled Java class file represent the magic number. A magic number (or file signature) is a short sequence of bytes at the very beginning of a file that uniquely identifies its true format and type. For example, a PNG Image file should start with those bytes: `89 50 4E 47`, a PDF Document file should start with those bytes: `25 50 44 46`, and so on.

But the magic number of Java class files is a little bit interesting. The very first thing in any compiled Java class file is the magic number: `0xCAFEBABE`. Yes, you read that right. It's literally "CAFE" and "BABE" in hexadecimal. I guess Java developers really loved coffee.

If a JVM implementation did not find the exact same sequence of bytes at the very beginning of the class file, it should abort execution process as it's not a valid class file and it wouldn't be able to parse it.

### Minor and Major Versions

After the first four bytes of the magic number comes two bytes: one for the `minor_version`, and another for the `major_version`. These tell you which version of the Java spec this class file was compiled against.

The major version is the important one. Different Java versions have different major version numbers. For example:
- Java 8: major version 52 (0x34)
- Java 11: major version 55 (0x37)
- Java 17: major version 61 (0x3D)

The minor version is rarely used in practice (usually 0), but it's part of the spec for forward compatibility. If you're running a newer JVM but encounter a class file with a future major version, you know this class file is too new for you.

## The Constant Pool

After the first 8 bytes of a compiled Java class file, the next two bytes represent a number which is the size of the constant pool entries that will be found after. The constant pool is something like a map or a list of constant pool entries. Each constant pool entry might represent a reference (like a class reference, method reference, field reference, etc) or a constant (like a String, Long, Float, etc).

According to the specs, a single constant pool entry takes the format:

```
cp_info {
    u1 tag;
    u1 info[];
}
```

This means that the first byte represents a tag, that is the type of this constant pool entry. Each tag byte must be followed by two or more bytes giving information about the specific constant which are the info bytes.

## Access Flags, This Class, and Super Class

After parsing the first 8 bytes of the class file header, the 2 bytes of the constant pool size, and the next bytes of the constant pool entries, there are 2 bytes representing a mask of access flags, 2 bytes representing a reference to this class in the constant pool, and 2 bytes representing a reference to its super class in the constant pool.

Please note that a single class file can have more than one flag set by taking the bitwise or of those flags. For example, if the `access_flags` two-bit value was `0x0021`, that is `0x0020` | `0x0001`, this means that this class is both `ACC_PUBLIC` and `ACC_SUPER` at the same time.

### This Class

The next two bytes represent a number which is an index to a constant pool entry that holds a reference to the main class of the current class file.

### Super Class

The next two bytes represent a number which is an index to a constant pool entry that holds a reference to the super class of the current class file. That is the class which the main class is a child class from, or that the main class inherits from. If the class has no parent class that it inherits from, then its super class is the `java/lang/object` class.

If the value of the super class two bytes is zero, then this class file must represent the class Object, the only class or interface without a direct superclass.

## Interfaces, Fields, and Methods

After the first 8 bytes of the class file header, 2 bytes of constant pool size, n-bytes of constant pool entries, 2 bytes of access flags, 2 bytes of this class reference, and 2 bytes of super class reference come the most complex parts of a class file.

The next bytes in the class file actually hold logic and bytecode that tells the JVM exactly how to function and integrate across its core components to achieve the required functionality. Let's go through them.

### Interfaces

The next two bytes represent a number which is the size of the interfaces array that will be found after. Each item in the interfaces array consists of two bytes, those two bytes represent a number which is an index to a constant pool entry that holds a reference to an interface class that the current class implements. That's it, this one is not so complex.

### Fields

The next two bytes represent a number which is the size of the fields array that will be found after. Each item in the fields array have the following structure:

```
field_info {
    u2             access_flags;
    u2             name_index;
    u2             descriptor_index;
    u2             attributes_count;
    attribute_info attributes[attributes_count];
}
```

The first two bytes are the access flags bytes which represent a mask, just like the access flags of the class file itself, but the access flags values of a field are different from that of the class file.

Please note that also a field's access flags are a mask which means that a single field can have more than one flag set. For example, if the `access_flags` two-bit value was `0x001A`, that is `0x0002` | `0x0008` | `0x0010`, this means that this field is`ACC_PRIVATE`, `ACC_STATIC`, and `ACC_FINAL` at the same time.

The next two bytes represent a number which is an index to a constant pool entry that holds a reference to a constant utf8 string that represents the name of that field. In other words, the name of the variable.

The next two bytes represent a number which is an index to a constant pool entry that holds a reference to a constant utf8 string that represents descriptor of that field. In other words, type of a class, instance, or local variable. You can head to section [4.3.2. Field Descriptors](https://docs.oracle.com/javase/specs/jvms/se8/html/jvms-4.html#jvms-4.3.2) for more information about the structure of the descriptor string.

The next two bytes represent a number which is the size of the field's attributes array that will be found after. 23 attribute types are predefined by the specs. Attributes will be discussed further in the next section.

## Attributes

The next two bytes represent a number which is the size of the attributes array that will be found after. Each item in the attributes array have the following structure:

```
attribute_info {
    u2 attribute_name_index;
    u4 attribute_length;
    u1 info[attribute_length];
}
```

The next two bytes represent a number which is an index to a constant pool entry that holds a reference to a constant utf8 string that represents the name of that attribute.

The next four bytes represent a number which is the size of the attribute's info array that will be found after. As I mentioned earlier, there are 23 different types of attributes, each one has a different sequence of info bytes.

You can head to section [4.7. Attributes](https://docs.oracle.com/javase/specs/jvms/se8/html/jvms-4.html#jvms-4.7) for more information about each attribute type.

One important thing to note is that not all the 23 attribute types need to be supported by your JVM implementation to function correctly. Five attribute types are essential for a base JVM which are: ConstantValue, Code, StackMapTable, Exceptions, and BootstrapMethods. Twelve attributes are critical to correct interpretation of the class file by the class libraries of the Java SE platform. Six attributes are not critical to correct interpretation of the class file by either the Java Virtual Machine or the class libraries of the Java SE platform, but are useful for tools

In this section, I will only talk about the Code attribute as it's the most important one and without it the JVM can not perform any logic or functionality. Also my JVM implementation (ZVM) only support the Code type attribute and lacks the rest at the moment.

### The Code Attribute

The Code attribute is the most important attribute type in the whole 23 types supported by the JVM specs. It contains information about the instructions and auxiliary information for a method. This means that it's the part that is responsible for holding the instructions that describe the logic or the functionality that a method must perform.

According to chapter 4 section [4.7.3. The Code Attribute](https://docs.oracle.com/javase/specs/jvms/se8/html/jvms-4.html#jvms-4.7) from the specs, the Code attribute structure looks like this:

```
Code_attribute {
    u2 attribute_name_index;
    u4 attribute_length;
    u2 max_stack;
    u2 max_locals;
    u4 code_length;
    u1 code[code_length];
    u2 exception_table_length;
    {   u2 start_pc;
        u2 end_pc;
        u2 handler_pc;
        u2 catch_type;
    } exception_table[exception_table_length];
    u2 attributes_count;
    attribute_info attributes[attributes_count];
}
```

Please note that the first two fields in the code attribute structure are duplicated from the original attribute structure. It's a very weird format from the specs, and I learned that the hard way, but that's why I'm writing this series of blogs in the first place. Let's talk about the other fields briefly.

The first two bytes of the code attribute are for the max_stack field which indicates the maximum depth of the operand stack of that method frame at any point of execution.

The next two bytes of the code attribute are for the max_locals field which indicates the number of local variables in the local variable array allocated upon invocation of this method, including the local variables used to pass parameters to the method on its invocation.

The next four bytes are for the code_length field which indicates the length of the code array of this method frame. The code array is the array that contains the required instructions to execute in order to perform the current method's logic or functionality. After that comes the code array itself which contains the actual instructions.

The Java Virtual Machine Specifications instruction set support ~202 instructions enough to perform any method logic or functionality. The instruction set will be discussed in a later blog, but if you want to know more about it, head to [Chapter 6. The Java Virtual Machine Instruction Set](https://docs.oracle.com/javase/specs/jvms/se8/html/jvms-6.html) of the specs.

The next bytes are specific to exception handling in Java code, specially the try catch statements. It describes the start and end of the code that is surrounded by the try statement, the exception type that is supposed to be catched, and more info about exceptions.

Finally, the code attribute itself can contain another types of attributes.
