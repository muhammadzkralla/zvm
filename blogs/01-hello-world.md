## How Java Compiles And Runs Your code?

Let's get back to your "Hello, World!" program, it looks something like this:

```java
class Main {
    public static void main(String[] args) {
        System.out.println("Hello, World!");
    }
}
```

You compile this code by running the `javac Main.java` command. One important distinction for you to know is that `javac` is the compiler and it has nothing to deal with the JVM, they are completely separate components that rely on each other sequentially.

For more clarification, the compiler is used first, it takes the java file path as an input parameter, opens the file and compile it, outputs another separate file called the "class file" with a ".class" extension, and here comes the end for the compiler's part of the process, it's not used again later to actually run your code.

Instead, here comes the role of the JVM when you run the command `java Main` to take that ".class" file as an input, parse it, and start actually running it and outputs the result, if any, to the terminal or perform a certain job like creating a file, responding to socket connections, or any other logic that you can perform using the Java programming language.

That's why Java has the slogan "Write once, run anywhere" (WORA). It's because that `.class` files are a standardized byte format any JVM implementation can read, whether it's OpenJDK's HotSpot (millions of lines, C++) or my little hobby `ZVM` (thousands of lines, Rust).

Please note that the compiler part is completely out of scope in this series of blogs, we will solely discuss the JVM part.

## Fetch, Parse, and Execute

After the compiler compiles your code and outputs the ".class" file, the JVM fetches that ".class" file, parses it and extract a huge amount of data which we will discuss later, and finally execute your logic, instruction by instruction.

Fetching a file is easy, any programming language has this feature and expose a very simple API to interact with file systems, so this is an easy step and has nothing complicated.

What about parsing this file? This is our first complex step in the building our JVM journey. When you read chapter 4 in the official [Oracle JVM Specs](https://docs.oracle.com/javase/specs/jvms/se8/html/jvms-4.html), you will see the class file structure that looks like this:

```
ClassFile {
    u4             magic;
    u2             minor_version;
    u2             major_version;
    u2             constant_pool_count;
    cp_info        constant_pool[constant_pool_count-1];
    u2             access_flags;
    u2             this_class;
    u2             super_class;
    u2             interfaces_count;
    u2             interfaces[interfaces_count];
    u2             fields_count;
    field_info     fields[fields_count];
    u2             methods_count;
    method_info    methods[methods_count];
    u2             attributes_count;
    attribute_info attributes[attributes_count];
}
```

Well, that's a lot of data to be parsed, but before explaining them to you, I want you to know that every single Java file transforms into this when you compile it, starting with your simple "Hello, World!" program, and going far up till the most complex microservices projects that exists. All represented by just those attributes of a class file.

Of course I will not explain every single one of them, but eventually we will interact with every single one of them while building our own JVM implementation, and then you will have an intuition about every single one of them.

But before parsing the class file, let's first understand this weird format. `u2` means "2 unsigned bytes", and the word next to it is the attribute name, this means that every line describes the size and the name of a class file attribute.

That's it, that's the entire contract. In my VM, this translates exactly into a struct ([src/parser/class_file.rs](https://github.com/muhammadzkralla/zvm/blob/develop/src/parser/class_file.rs)):

```rust
pub struct ClassFile {
    pub magic: u32,
    pub minor: u16,
    pub major: u16,
    pub constant_pool_count: u16,
    pub constant_pool: Vec<CpInfo>,
    pub access_flags: u16,
    pub this_class: u16,
    pub super_class: u16,
    pub methods: Vec<MethodInfo>,
    // ...
}
```

The beauty of the class file format is that the whole thing is just a sequence of bytes you can walk through linearly. My reader is basically a cursor (`read_u1`, `read_u2`, `read_u4`, `read_utf8`) advancing through the file, interpreting each chunk according to the specs, and converting it into these structs.

In a later blog, we will discuss parsing in details, but for this one I want to keep things abstracted to give you just an overview.

## Virtual Machine Core Components

### The Stack Frame

The first core component I want you to know is the stack frame. The stack frame is a component that represents a method or a function. Any function you write in code translates into a stack frame waiting to be pushed on the call stack (which is another core component we will talk about after this one) inside the virtual machine. A stack frame itself is composed of other core components or parameters like `method_name`, `operand_stack`, `local_variables`, `bytecode`, and `pc` (program count register).

In my VM, this translates almost exactly into a struct ([src/vm/stack_frame.rs](https://github.com/muhammadzkralla/zvm/blob/master/zvm/src/vm/stack_frame.rs)):

```rs
/// Method execution stack call frame
#[derive(Clone)]
pub struct Frame {
    pub method_name: Option<String>,
    pub operand_stack: OperandStack,
    pub local_variables: LocalVariables,
    pub pc: usize,
    pub bytecode: Vec<u8>,
}
```

### The Call Stack

The `call_stack` is a stack for stack frames discussed in the above section. When the virtual machine wants to execute a function logic, it pushes its stack frame onto the call stack. Every single thread has its own call stack and that's why you can execute different logic at the same time using different threads, because each thread of them has its own separate call stack that consists of its stack frames.

The virtual machine pops the first stack frame off the call stack (which is typically the stack frame that represents the main function) and starts executing it by moving its `pc` (program count register) in the `bytecode` extracted from the code attribute of that stack frame. Please remember that I'm trying to give you an overview, so don't get overwhelmed if you don't fully understand for now.

### Bytecode and Program Count Register

The `bytecode` is a set of bytes that represent the instructions that are required to be done to actually execute the function logic, remember that `bytecode` is a part of a `stack_frame` that is the part that represents functions that performs certain logic. If you read chapter 4 from the specs, you will find that extracting the `bytecode` of a `stack_frame` is not really straight forward. You need to parse the class file attributes first, then go to the `Code_attribute`, then the `code` attribute. Again we will not dive into details for now.

A `pc` program count register is used to store something like an index pointing to the current byte being processed in the `bytecode` set of bytes. It helps the virtual machine know which instruction should it execute at the moment.

### The Operand Stack

The `operand_stack` is a core component of the `stack_frame` which is a core component of the `call_stack` which is itself, well, a core component. I hope you are not confused. Anyway, the operand stack is a stack for values. This value can be an integer, float, long, a reference to an object or an array, or any other value type that is supported by the JVM specs that you can find in chapter 2. The `operand_stack` helps the virtual machine perform arithmetic operations on values, storing or accessing values in arrays, or deal with values and objects in general.

### The Instruction Executor

Here comes the big boy of the virtual machine's core components, the instruction executor is the component that actually performs the function logic by decoding the instruction bytes, fetching the required instruction, and starts actually executing it. If you read chapter 6 in the specs, you will find that the JVM instruction set is ~202 instructions, some of them are reserved.

Chapter 6 is actually one of the most straight forward chapters of the specs. You will find it explaining each instruction by telling you the byte that represents it, its format, description, what it does to the `operand_stack`, and its behavior in general.

To build your own virtual machine you have to read all of them and go one by one implementing each one correctly handling the `operand_stack`, `call_stack`, `local_variables`, `runtime`, and any other virtual machine components.

### Other Core Components

There are many other virtual machine core components to understand like `runtime`, `heap`, `garbage collector`, and others. However, I want to keep this blog an abstracted overview and not to make it a long comprehensive guide, so I will stop here and discuss more details in later blogs.

## Explain "Hello, World!" Internally

Returning to our first thesis, how could you explain the simple "Hello, World!" program in terms of JVM internals? Let's revisit the code to this program:

```java
class Main {
    public static void main(String[] args) {
        System.out.println("Hello, World!");
    }
}
```

Let me introduce you to the `javap` tool. The `javap` command is a built-in JDK tool known as the Java Class File Disassembler. It takes class files as an input and disassembles it to the corresponding bytecode in a human-readable format. Let's run `javap -c Main.class` and see the output:


Let's analyze this output. The first line is something related to my local environment as I use a tool called `lombok` as an agent attached to any Java file I use. You don't have to know anything about that.

The second line says that this bytecode was generated from a compiled file called "Main.java", and this is pretty much self-explanatory. Now let's get to what really matters, the actual bytecode.

```bash
Main();
Code:
0: aload_0
1: invokespecial #1                  // Method java/lang/Object."<init>":()V
4: return

```

This part represents the `Code_attribute` of a function called "Main()" and this is the base constructor of the "Main" class. The numbers in the prefix declares the `pc` index of that instruction and then the name of that instruction. In the case of this function, it's composed of three instructions: `aload_0`, `invokespecial`, and `return`. You can see chapter 6 in the specs to know exactly what each one does, but I will give you a brief now. `aload_0` loads the reference located at index 0 from the `local_variables` of the current `stack_frame` and pushes it onto the `operand_stack`. `invokespecial` tells the JVM to invoke the superclass constructor if exists. `return` tells the JVM to return from the current `stack_frame` without any return value.

Please note that this bytecode will never execute as we didn't call the constructor in our code, but the compiler generated it for us anyways, so it exists in the bytecode but with no effect.

```bash
public static void main(java.lang.String[]);
Code:
0: getstatic     #7                  // Field java/lang/System.out:Ljava/io/PrintStream;
3: ldc           #13                 // String Hello, World!
5: invokevirtual #15                 // Method java/io/PrintStream.println:(Ljava/lang/String;)V
8: return
```

This part represents the `Code_attribute` of a function called "main()" and this is the main function of our program. `getstatic` loads a reference located at `constant_pool` index #7 and pushes it onto the `operand_stack`, this is a reference to the printing function. `ldc` loads a constant located at `constant_pool` index #13 and pushes it onto the `operand_stack`, this is a reference to a String with value "Hello, World!". `invokevirtual` tells the JVM to invoke the printing function that takes a String as an argument and returns void. `return` tells the JVM to return from the current `stack_frame` without any return value.

You see? All that for just than one single print "Hello, World!" line, but now you can fully explain it in boring details! Imagine more complex microservices program? Yes we definitely needed that layer of abstraction to build high-level applications.

## Conclusion

You write Java code in a "Main.java" file, you compile this file using the `javac Main.java` compiler, it generates the corresponding java bytecode in a separate file "Main.class", you run this file using the `java Main` JVM that takes that class file and actually starts executing it instruction by instruction after parsing it.
